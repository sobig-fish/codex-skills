# 经验复盘：从一个有趣想法到可复用案例

这份复盘记录需求拆解与工程方法，不公布真实业务统计、成员身份或内部系统信息，也不把未验证的效果写成成功案例。

## 先确认语义，再动手实现

“事件合约”“预测”“倍率”容易让人联想到不同产品。实现前应把行为写清楚：参与者保存的是什么，确认结果后改变什么，有没有资金、实物或可兑现权益。

本案例最终范围很明确：**只保存模拟判断和命中记录，无购买、转让、兑换或奖励**。奶茶是视觉主题，模拟倍率是历史参考比例的展示变换。范围必须体现在数据字段、接口、按钮、规则弹窗和说明文档里，不能只靠页脚的一句话。

从旧功能改成新范围时，应检查是否还残留余额、积分榜、奖励文案或可误解的“结算”提示。兼容已有数据库结构可以是迁移策略，但保留的旧字段不能继续驱动已经取消的产品行为。

## 把口头时间描述变成可测试区间

“周三开放”“周四截止”“到点公布”仍然缺少边界语义。需要继续追问：审核期间能不能参与，截止那一刻算不算有效，没有人工结果时怎么办，错过审核是否补发。

本案例把审核与参与分开：上周三 11:00–12:30 前审核，12:30 起开放，上周四 18:00 起锁定；当周三 11:00 后允许管理员确认结果。每个区间采用明确的包含与排除关系，避免不同页面各自解释。

前端倒计时用于帮助理解，服务器时间用于判断操作。倒计时归零不应制造不存在的结果，也不能绕过审核。测试应覆盖每个边界之前、恰好到达与刚刚之后，而不只是随便挑一个周内时间。

## 先证明分类无歧义

“0”“小于阈值”“等于阈值”“大于阈值”看起来有四项，实际前两项重叠。先修正为“0”“1 至阈值减 1”“等于阈值”“大于阈值”，再做界面，比上线后解释双重命中便宜得多。

这条方法也适用于表单状态、工单优先级和容量区间：类别必须互斥，而且要覆盖所有合法输入。非法输入应明确拒绝，不能偷偷截断小数、把负数改成零，或把无效日期挪到另一天。

## 身份、权限与分享不是一回事

“使用同一个工作区账号”只能帮助建立身份来源，不能自动回答谁能看站点、谁能参加活动、谁能确认结果。

本案例分开维护站点查看权限和应用成员角色。加入成员名单不等于完成站点分享；反过来，能打开站点也不等于拥有管理员权限。

可复用的做法是：先写出每个接口允许谁做什么，再把同样的角色、有效状态和时间条件放进真实写入路径。让用户 ID 来自可信认证层，避免由客户端任意指定；使用明确管理员配置，避免抢占式的“首位访问者即管理员”。

平台专用身份适配也是边界的一部分。公开仓库能分享这种设计思路，但不能因此宣称任何 GitHub 页面都能直接用 GPT 账号登录。

## 历史表不等于事实来源已经解决

表中有一个数字，不代表已经知道它是报名、计划、登记、到场还是最终完成数量。应该先记录字段口径，再决定能否拿它来解释未来事件。

几个容易被忽略的问题：

- **无记录不等于零。**只记录有人的周，会让零事件类别在历史中显得过少。
- **登记不等于完成。**取消、补录和统计日期变化都可能改变最终数量。
- **最近若干条不等于最近若干周。**缺失期会拉长实际时间跨度。
- **分项需要核对。**总量与不同日期的分项可能采用不同口径；算法无法替业务负责人解释。
- **旧分布会漂移。**团队规模、流程、政策和季节变化可能让同样的历史窗口失去参考价值。

因此，源表采用只读导入，网站需要的仅是最小化汇总。应用内部修改活动参考数或确认实际结果，不应反向改写原始登记表。

## 防止“事后知道”混入“事前预测”

过滤目标周之后的记录只是第一步。还要问：模型作出判断的当时，前一周的结果是否已经可用？一条历史记录是不是之后才补上的？

本案例按审核开始时间建立可用截止线，并保守排除在同一时刻才达到业务确认时间的上一周。回看验证也使用同样的时间规则。

这仍不能消除全部信息泄漏：如果数据没有录入时间、修订时间和当时快照，就无法准确重建过去真正看得到的内容。因此 MAE 只能标为按业务时间回看的误差参考，不能包装成真实的事前预测战绩。

更可靠的下一步是从新活动开始保存输入快照、可用时间和配置版本，再积累前向验证记录。不要用一个更复杂的模型掩盖来源时间不清的问题。

## 可解释性也包括承认“不知道”

小样本比例、轻度平滑、分位范围和倍率上限都有各自的用途，但不能合并成“预测已经很准”的结论。

平滑避免零频次直接导致无穷大的倒数，不意味着某个从未观察到的事件有了已证实概率。20× 是展示上限，不是风险控制能力。多个类别显示相同上限也很正常。

没有可用样本时，应显示“暂无参考”。把空数组计算产生的 0 展示为预计数量，是把实现占位误当业务事实。参考比例、展示倍率和已确认实际结果应在界面中分别标识。

## 并发与审计要落在写入那一步

页面加载时确认用户是管理员，并不能保证提交时角色仍有效；展示“活动开放中”，也不能保证请求到达时仍未截止。

因此原应用采用条件写入：数据库同时检查当前角色、有效成员状态、时间、配置版本和活动结果状态。唯一键使同一期同一用户的修改成为覆盖，而不是新增另一份记录。

审计也不能只在前端成功提示后补写。业务变更和审计应绑定在可验证的事务路径内，并检查到底有没有变更成功。版本冲突应明确返回，避免把“没有写入”显示成“已经保存”。

这不等于所有并发问题都已消失。结果更正若要防止操作者基于旧页面覆盖新结论，还需要携带其看到的版本。读写间的版本比较与跨页面的陈旧状态检查是两种不同保证。

## 分层验证，分别报告

| 层次 | 应当检查什么 | 不能据此声称什么 |
| --- | --- | --- |
| 纯算法 | 日期、边界、互斥类别、无效值、缺失、重复、未来数据、倍率取整 | 登录与数据库权限已经正确 |
| 服务端接口 | 身份、角色、时间、规则版本、请求来源、参数与冲突 | UI 所有交互已可用 |
| 数据库环境 | 唯一约束、条件写入、事务回滚、审计与并发结果 | 现实事件数量已经核实 |
| 浏览器 | 手机与桌面布局、弹窗、键盘操作、错误反馈、刷新后状态 | 历史模型具有稳定预测能力 |
| 业务确认 | 实际结果口径、管理员依据、修订记录 | 未来结果可以保证 |

本目录只提供其中可独立运行的纯算法提取包。`npm test` 与 `npm run demo` 的执行结果，应由使用者在当前提交上实际运行后记录。这里不列未经本次执行确认的通过数量、部署状态、准确率或用户反馈。

## 对外分享时，分享方法而不是内部数据

可复用价值来自规则边界、数据合同、验证方法和失败处理，不需要附带真实人员名单或内部表格。

发布前应检查文件内容与提交历史，移除真实统计、姓名、邮箱、私有站点地址、项目标识、表格链接、凭据和运行缓存。示例数据应重新生成，并明确标记虚构；仅把姓名替换掉，仍可能留下可识别的业务信息。

一个诚实的案例应清楚写出：哪些代码可以本地运行，哪些只是原架构说明，哪些功能依赖特定平台，哪些事情尚未验证。它的价值是让别人少走一段弯路，而不是制造“一键复制就能上线”的错觉。
