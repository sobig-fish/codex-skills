# 如何适配自己的团队

## 1. 先确定访问范围

先确认使用哪个账号和工作区创建站点，再读取当前站点的分享能力。不要根据别人的界面、同一个域名或历史经验推断自己拥有外部邀请或公开发布权限。

把平台准入和应用准入分别验证：

| 平台允许访问 | 应用成员启用 | 结果 |
| --- | --- | --- |
| 否 | 任意 | 平台入口拒绝，应用名单不能绕过 |
| 是 | 否 | 登录成功后，应用拒绝业务访问 |
| 是 | 是 | 继续检查具体操作的角色和资料范围 |

跨工作区的人能否参与，须在目标环境确认外部访客能力。向应用名单添加一个邮箱，不会创建平台邀请，也不会自动让对方成为工作区成员。[官方分享说明](https://learn.chatgpt.com/docs/sites/publishing-and-sharing)

## 2. 替换身份适配器

示例中的 `loadVerifiedClaims` 是服务端注入的依赖；`demo.mjs` 里的实现只返回合成数据，不能用于真实登录。

真实接入有两类路径：

- **Sites 托管环境**：使用当前模板提供的服务端认证帮助函数及平台登录入口；先确认请求确实经过平台身份边界，再把已验证结果映射为示例要求的 `subject`、`email` 等字段。适配器中的 `issuer` 和 `audience` 需要与自己服务端的配置一致，它们不是浏览器可以声明的授权凭证。
- **其他托管环境**：接入该环境支持的 OIDC、SSO 或服务端会话验证器。令牌的签名、签发方、受众及有效期由该验证器处理，再交给本案例的成员策略。不要把 Sites 请求头的名称照搬为公网身份验证方法。

本案例没有实现通用“使用 ChatGPT 登录任意网站”的 OAuth 客户端。不能只复制几个请求头就获得这项能力。

## 3. 建立最小成员名单

为管理员显式配置已核验身份，避免首访自动获权。把展示资料与授权名单分开维护，姓名与邮箱只作展示或邀请信息。

示例按稳定的、站点范围内的用户标识授权，不按邮箱后缀授权。新站点的用户标识可能不同，迁移时重新绑定。真实邀请绑定应确保：邮箱由可信身份提供方验证、账号尚未绑定、并发绑定只有一次成功、撤销后每个写接口都立即拒绝。

## 4. 替换合成资料

修改 `example/team.mjs` 可以先验证团队分组与搜索。公开仓库继续使用合成数据；真实名单、工作邮箱和内部介绍应由私有数据源或受控管理入口提供，避免写入公开源码或前端静态包。

本例目录接口只返回展示 ID、姓名、小组、城市和介绍。个人联系方式、账号标识及管理字段默认不包含在响应中。展示范围也需要团队自己确认，登录保护不等于所有信息都适合所有成员查看。

## 5. 进行真实环境验收

本地测试之后，至少用授权测试账号验证：

1. 未登录及未加入平台受众的人被正确拦截。
2. 已登录但不在应用名单中的人被拒绝。
3. 普通成员可以看目录、修改自己被允许修改的内容，不能管理他人。
4. 管理员权限来自服务端名单，伪造前端 `role` 或身份请求头不能提升权限。
5. 停用成员后，其下一次请求被拒绝；个人资料不会被未授权接口返回。
6. 如果确实开放外部访客，使用对应的外部测试账号完成访问验证，并检查其不会获得编辑或工作区成员权限。

示例没有网络服务、数据库写入和真实会话。上述真实环境验收需要在实际部署中完成，不能用本地测试结果替代。
